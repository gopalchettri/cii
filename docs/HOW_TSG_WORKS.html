Threat Scenario Generator (TSG v2) · internal design

How TSG Works

TSG turns an asset record into reviewed threat scenarios, mapped controls and remediation plans, with public evidence when external intelligence is on. This document explains how it works, end to end, at three levels of detail.

1In short

For one asset, TSG answers: which cyber-attacks really matter here, how would they unfold, and what reduces them?

  1. A run is requested for one asset and its supporting systems.
  2. TSG reads the asset's facts from the platform database and freezes them for the whole run.
  3. It shortlists threats from our own curated threat library and asks the AI which really apply to this asset, and why.
  4. It plans one scenario per kind of attack and per route through the systems, writing the most informative ones first.
  5. The AI writes each scenario. Code rules and a second AI check verify it. With external intelligence on, every scenario must cite public evidence.
  6. It maps controls from our control library to each scenario.
  7. People accept or reject each scenario, and TSG drafts a remediation plan for an accepted one.

What TSG guarantees

  • Threats come from our curated library first.
  • Every AI answer is checked by code before it is used.
  • Every scenario, control, AI call and decision is stored and auditable.
  • Each entity sees only its own data.
  • A person makes every final decision.

What TSG never does

  • Present an attack as having happened: scenarios say "could" and "may".
  • Claim a system is vulnerable without proof.
  • Add an AI-proposed threat to the library without a curator's approval.
  • Send passwords, keys or database IDs to the AI.
  • Let text from outside sources give the AI instructions.

Frozen facts

SQL Server is read once, at the start. Every later step uses that frozen copy, so a run never sees a half-changed asset.

Sets

The first 6 scenarios are written right after planning, so reviewers can start. Each "next set" request writes 6 more; nothing is written without a request.

Attack path

One scenario for each kind of attack (STRIDE) on each route, the set of systems the attack goes through. Paths are ranked to cover high-impact threats, every system and every kind first.

Intelligence off

All seven steps run the same way, without evidence, real attacker groups or UAE/Gulf ranking.

4How search works

TSG never asks the AI to recall a library from memory. It first narrows the library down with hybrid retrieval, and only then lets a reranker or the AI judge a short list. The same technique is used in five places.

BM25 keyword score
Matches exact words. Rare words weigh more, and short texts are favoured a little.
Embedding + cosine
Matches meaning. Each text becomes a vector of 3,072 numbers on the laptop and 4,096 in UAT; similarity is the cosine between two vectors. When any candidate reaches 0.60, weaker ones are ignored.
Reciprocal Rank Fusion
Combines the two rankings: each list gives a candidate 1 / (60 + rank). Ranks are combined rather than scores, because a BM25 score and a cosine cannot be compared.
Filter before ranking
The STRIDE kind, or the IT/OT type, is applied before the top-k cut, so a wrong candidate never takes a place.
Cross-encoder reranker
A model that reads the query and a candidate together and scores the match from 0 to 100. It is used where precision matters.

5Where AI is used

Rules for every AI call

  • One client for all calls, through LiteLLM.
  • At most 16 calls in flight across all workers, using Redis slots.
  • Short failures are retried 3 times (0.5, 1, 2 s); after a timeout, the fallback model is tried.
  • Each call is recorded in tsg_ai_calls for 14 days.
  • Secrets, keys and database IDs are redacted before sending.
  • Facts are sent as clearly marked data, never as instructions.

Models

  • Chat: Kimi-K2.6 on the laptop; kimi-k2.5 in UAT, with glm-5 as fallback.
  • Embedding: text-embedding-3-large (3,072) on the laptop; qwen3-embedding-8b (4,096) in UAT.
  • Reranker: bge-reranker-v2-m3, run locally, on the laptop; qwen3-reranker-8b in UAT.

6External intelligence

This feature is optional and switched by EXTERNAL_INTELLIGENCE_ENABLED. When it is on, TSG uses retrieval-augmented generation (RAG) with guardrails: it retrieves verified records from public feeds, gives the AI only those as numbered facts, and checks every citation the AI writes. There are two separate pipelines: ingestion keeps a searchable copy of the feeds up to date in the background, and the query pipeline finds evidence for each scenario at write time. A plain-English explanation of what evidence means is in What Is Evidence?

8Reliability, security and operations

Reliability

  • Lease: a worker claims a job for 120 s and renews it every 30 s. Writes are fenced: they succeed only while that worker holds the lease.
  • Epoch: a job's generation number, so an old duplicate message does nothing.
  • Reaper: runs every 60 s and re-queues lost or unsent jobs.
  • Retries: an AI outage is retried after 15, 30, 60 and 120 s, up to 5 attempts.
  • One run at a time: one active run per asset, and the same Idempotency-Key returns the same run.
  • Acknowledged when finished: a crash loses no message.
  • Swapped whole: the library and the intelligence snapshots are replaced in one step, never half-way.

Security

  • API keys are stored as SHA-256 hashes and can be revoked.
  • Four identity headers are required on every call.
  • Every read is filtered by entity.
  • SQL Server is reached only through stored procedures.
  • The admin API needs a separate admin key.
  • Requests are limited to 2 MB.
  • Secrets are redacted before any AI call.
  • Feed text that reads as an instruction to an AI is quarantined.
  • The audit trail is kept for 365 days.

Operations

  • /health (the process is alive), /ready (every database answers and every queue has a live worker), /metrics.
  • Grafana dashboards and Alertmanager alerts.
  • Logs in Loki, with a request ID on every line.
  • Flower for Celery tasks.
  • On the laptop, run.ps1 start|stop|status.

9Glossary

STRIDE
The six kinds of threat: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege.
Run / session
One request to generate scenarios for one asset (a tsg_sessions document).
Attack path
One kind of attack on one route through the asset's systems; one scenario each.
Set
Scenarios written in one go: 6 after planning, then 6 per "next set" request.
Frozen facts
The asset and system facts saved at the start of a run and never re-read during it.
Fact sheet
The redacted text about the asset and its systems that the AI reads.
Embedding / vector
A list of numbers that represents the meaning of a text; similar meanings give similar vectors.
Cosine
The similarity of two vectors (1 = the same meaning).
BM25
Keyword scoring in which rare words count more.
RRF
Reciprocal Rank Fusion: combines two rankings by adding 1 / (60 + rank).
Reranker
A cross-encoder model that reads a query and a candidate together and scores the match from 0 to 100.
RAG
Retrieval-augmented generation: the AI writes only from facts that were retrieved and handed to it.
LLM-as-judge
A second AI call that checks the first one's work against the facts.
Relevance gate
The AI check "does this threat apply to this asset, and why?"
Gap-fill
One AI-proposed threat, only when a whole STRIDE kind found nothing in the library.
Evidence
A public record that a technique or flaw is used by real attackers, cited in a scenario as [n].
Snapshot
A frozen, checksummed, searchable copy of the feeds that every worker loads into memory.
Quarantine
Feed text held back because it reads like instructions to an AI; it is never indexed.
Lease, epoch, fenced write
How a job is owned by exactly one worker, and how a stale worker is prevented from overwriting newer work.
Reaper
A task run every 60 s that re-queues lost jobs.
