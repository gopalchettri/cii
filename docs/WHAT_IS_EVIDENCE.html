What is evidence?

You have two reports for the Traffic Control Platform: one made without external threat feeds, one made with them. The second has an extra section under every scenario called Evidence. This page explains what that is and how the tool produces it.

The short answer

Evidence is a published, public record showing that this kind of attack has really been used by real attackers.

Each scenario points to its evidence with a number such as [1], like a footnote in a report. Under the scenario, the tool lists the source, a link, and the facts it took from it, so anyone can open the link and check.

Without external feeds, a scenario is a well-reasoned "this could happen". With them, it becomes "this could happen, and here is proof that attackers really do this".

The three vulnerability sources describe flaws in specific products, and the platform records no product list for this asset, so the tool does not cite them. It will not claim "your system has this flaw" without knowing the product.

How it is achieved: the evidence pipeline

When EXTERNAL_INTELLIGENCE_ENABLED=true, scenario writing becomes retrieval-augmented generation (RAG) with guardrails. The AI is never trusted to "remember" threat intelligence. The tool first retrieves verified records from the feeds, gives the AI only those, and then checks what the AI wrote against them. There are six stages: the first two run in the background, and the other four run every time scenarios are written.

  1. 1

    Ingestion: collect and normalise the feeds

    Background, scheduled
    • Scheduler: a Celery beat job runs every hour and fetches each source that is due. CISA KEV, EPSS, NVD and the ICS advisories are fetched every 24 hours; MITRE ATT&CK (the Enterprise and ICS STIX bundles) every 168 hours.
    • Download: over HTTPS with a conditional request (ETag / If-None-Match), so an unchanged file is not downloaded again. Size limits and the sources' rate limits are enforced.
    • Normalisation: each item becomes one record with the same fields: source, ID (e.g. T0859, a CVE number), kind (technique, vulnerability or advisory), title, text, link, an IT or OT tag, and structured data (attacker goals, mitigations, and the real groups and campaigns that used it).
    • Sanitisation: every field is length-capped and stripped of control characters. Text that matches prompt-injection patterns (text written to give an AI instructions) is quarantined and never indexed. Today 3 ATT&CK records are held back this way.
    • Versioning: each record carries a content hash. A change creates a new version and retires the old one, so the history is kept. Records are stored in MongoDB.
  2. 2

    Indexing: build a searchable snapshot

    Background, after each refresh
    • Corpus: all current records are assembled. Exploit scores (EPSS) and vulnerability details (NVD) are joined to their CVE, and indicators such as IP addresses and file hashes are removed from the search text.
    • Embeddings: each record's text is turned into a vector, a long list of numbers that captures its meaning. The laptop uses text-embedding-3-large (3,072 numbers per text) and UAT uses qwen3-embedding-8b (4,096). Vectors are cached, so only new or changed records are embedded.
    • Two indexes over the same records: a BM25 keyword index, which matches exact terms, and a vector index, which matches meaning by cosine similarity.
    • Snapshot: the result is fixed and identified by a checksum. Each worker loads it into memory and switches to a new snapshot in one step, never half-way.
  3. 3

    Retrieval: find the matching records for each scenario

    At write time
    • Query: built from the threat being written, as Threat: <type>: <name> plus Reason: <why it applies to this asset>. It is at most 700 characters, with personal data removed.
    • IT/OT filter: only records whose tag fits the asset are searched. The filter is applied before ranking.
    • Hybrid search: all queries in a batch are embedded in one call. Each query is searched in both indexes, and the two ranked lists are merged with Reciprocal Rank Fusion (RRF, k = 60), which rewards records ranked high in either list. The top 6 become candidates.
    • Reranking: a cross-encoder reranker model reads the query and each candidate together and scores relevance from 0 to 100. The laptop uses bge-reranker-v2-m3 and UAT uses qwen3-reranker-8b.
    • Selection rules, in this order:
      • a score below the calibrated threshold is dropped;
      • a vulnerability or advisory that cannot be tied to a product recorded for the asset is dropped;
      • an affected version that does not match is dropped;
      • a duplicate is dropped;
      • the best 3 per threat are kept.
      Every candidate's score and decision is recorded.
    • Fallback: if nothing qualifies, the search is repeated with two other wordings of the query. This needs no AI call.
    • Facts: each kept record is turned into at most 6 plain sentences built from its structured fields, for example "The 2015 Ukraine Electric Power Attack campaign used this technique." The evidence is saved on the plan, so a retry or regenerate reuses the same evidence and numbers.
  4. 4

    Generation: the AI writes the scenario with citations

    At write time
    • Prompt: asset facts, the threat, and the numbered facts. The facts sit inside a delimited block (<<<UNTRUSTED_EVIDENCE_BEGIN>>> … END), and the AI is told to treat that block as data, never as instructions.
    • No references in the prompt: the AI receives fact sentences only, never IDs, links or titles. It cannot invent or alter a reference, because it never handles one; the tool attaches the links afterwards.
    • Output: the scenario statement and risk statement with [n] markers, plus, for each marker, the claim it supports. The model is Kimi K2.6 on the laptop, and kimi-k2.5 with glm-5 as fallback in UAT.
  5. 5

    Validation: guardrails check the draft

    At write time
    • Deterministic rules in code, each of which blocks the draft:
      • at least one citation, and every [n] exists;
      • each marker has its claim;
      • no IDs or URLs inside the prose;
      • a real attacker or campaign is named only with its marker;
      • no "is vulnerable" or "is exploitable" when it is unknown whether our product is affected;
      • no echo of injected text;
      • an "it happened before" sentence must match what its source names;
      • a claim about the UAE needs a UAE-labelled source.
    • LLM-as-judge: the plan-check AI call, already made for every scenario, reads each claim against its evidence and lists any citation it does not support.
    • Outcome: any failure leads to one rewrite with the exact findings. If the draft still fails, it is blocked: kept for audit, never shown. Another attack path is written in its place.
  6. 6

    Storage and audit: full traceability

    At write time
    • The scenario stores the evidence it cites, numbered in the order first cited, with the link and facts. Its evidence mode is "source-documented".
    • The audit record keeps the query, the IT/OT filter, the snapshot ID, the threshold, the reranker model, and every candidate with its score and decision.
    • The plan records which snapshot and source versions it used. One audit-log entry is written per batch.

The rule that matters: with feeds on, every scenario you see cites at least one public source that passed stages 3 and 5. A scenario that cannot be backed by a source is dropped, and another attack route is written in its place.

Where the data lives in MongoDB

Everything is stored in the MongoDB database cii_tsg. The four intelligence collections (feed status, records, snapshots and the feed vectors) exist only while external intelligence is switched on; the others are part of every run.

tsg_intelIngestThe normalised records: ID (T0859, CVE-…), kind (technique, vulnerability, vulnerability detail, exploit score, advisory), title, text, link, IT/OT tag, structured data, content hash, state (valid or quarantined) and fetch time. tsg_embeddingsIndexVectors, one per text and model, so a text is never embedded twice. Corpus external_intelligence holds the feed records (5,293); the other corpora are our own library: threats, threat actors, threat types and controls.
tsg_external_intelligence_snapshotsIndexOne document per built snapshot (checksum, counts, embedding and reranker models, source versions), plus the 'active' pointer that tells every worker which snapshot to load.

What evidence means, and what it does not

It means

  • This method of attack is real and documented by a recognised authority.
  • Named real campaigns or attacker groups have used it.
  • There are published ways to reduce it, which help in choosing controls.

It does not mean

  • The Traffic Control Platform has been attacked.
  • Our system is confirmed to be vulnerable.
  • It happened in the UAE, unless the source is labelled "this country".

Since 14 October

New reports go one step further. Beside the threat actor, each scenario names up to three real attacker groups known for that attack, with groups that attacked the UAE or the Gulf region listed first. For example: APT33, a state group that attacked the region and your sector. Each source is also labelled this country, regional or global, and a story may only say something happened in the UAE if it cites a UAE source.

Not yet included: UAE incident feeds (aeCERT, UAE Cyber Security Council, DESC). They have no feed the tool can read yet and need legal approval first. Until then, most evidence is global.
